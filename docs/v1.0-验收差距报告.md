# v1.0 验收差距报告（系统性验证）

**验证日期**：2026-09-17
**被验版本**：v0.9.23（实机 `version = 0.9.23`）
**验证依据**：`docs/dsh-model-router-方向性指导方案.md` §2.2 / §5.2 / §6 / §9
**验证方式**：文档判据逐条对照 + **实机/代码实证**（不依赖「读代码猜」）

## 〇、先说结论

> **v1.0 不是「功能版本」，是「工程交付版本」。**
> 设计文档 §6 阶段 B 明确定义：**「不加新功能，把已有能力变成可信赖的稳定契约」**。
>
> 当前状态：**功能层已达「可用」（9 项核心能力 6 项达标），但 7 项工程化要求 0 项完成**
> （1 项半完成、1 项**恶化**）。
>
> → **距 v1.0 的差距全部在工程化，不在功能。**

## 一、v1.0 的定义（原始设计原文）

**§6 阶段 B：v1.0.0（契约冻结与交付收口）**
> **主题**：**不加新功能**，把已有能力变成可信赖的稳定契约。
> **阶段目标**：对外契约稳定，交付自动化。

**7 项要求**（§6 原文）：

1. 契约文档化：`/api/model-router/*` 端点、config schema、落盘格式（含渠道档案）三类契约显式文档化，并标注「稳定 / 实验」
2. 配置 schema 版本化与迁移链：新增字段可迁移，修复 `timeZone` / `mode` 持久化断链
3. 升级/回滚机制：安装、升级、回滚不依赖手工文件操作
4. 集成测试：真跑一次跑批的端到端用例 + API 契约断言
5. 多 provider 段场景实机验证：段合成规则的边界、落盘格式向后兼容
6. 前端可维护性：`client.js` 单文件已 2388 行，需建立模块边界
7. 安全边界测试化：「不读 API Key」由测试守住，而非仅写在文档里

**5 条验收判据**（§9.2 原文）：
- 三类契约（端点 / 配置 / 落盘，**含渠道档案**）有 schema 文档
- 配置迁移链可用：版本升级后配置不丢失（含 `timeZone` / `mode`）
- 多 provider 段场景实机通过
- 安装 → 升级 → 回滚全流程不依赖手工文件操作
- 单测 + 集成测试双层通过；「不读 API Key」有测试守住

## 六、诚实评估：能否达成 v1.0

**可以，但需要明确取舍**：

| 项 | 评估 |
| --- | --- |
| #1 #2 #4 #7 | ✅ **可行**，工程量大但风险可控 |
| #3 | ✅ **可行**，但「不依赖手工文件操作」对 DSH 插件形态有约束（插件装在宿主 node_modules 里，升级本质是替换目录）——**需先确认可行的自动化边界** |
| #5 | ✅ **可行**，但会**真实消耗 API 额度**（需跑批），且需要至少 2 个 provider 配置成不同段 |
| #6 | ⚠️ **风险最高**。3126 行单文件拆分是**纯重构**，无功能收益，但**回归风险大**（前端无自动化测试，只能靠 mock 渲染验证）。<br>设计文档把它列为 v1.0 要求，理由是「当前改动风险的主要来源」——**但拆分本身也会引入风险**。<br>**建议**：拆成 3–4 个逻辑模块（不追求细粒度），并用现有 mock 渲染测试兜住。 |

### 我的建议（分两批）

**第一批（低风险、高确定性）**：#7 → #1 → #2 → #4
→ 完成后即可满足 §9.2 判据中的 **4/5 条**（契约文档 ✓ / 迁移链 ✓ / 集成测试 ✓ / 安全测试 ✓）

**第二批（需验证/高风险）**：#5 → #3 → #6
→ #5 需真实跑批；#3 需确认自动化边界；#6 需接受重构风险
