## 2. 范围界定与拆分建议

### 2.1 两条规划线的关系

v0.9.9 同时受两份文档约束，但它们描述的是**两个不同层次的东西**，容易混淆：

| | 测试档案（Test Archive） | 渠道档案（Channel Profile） |
| --- | --- | --- |
| 记录什么 | **一次跑批的结果** | **一个渠道的限制脾气** |
| 粒度 | 每次跑批一条 | 每渠道一条（跨时间累积） |
| 存储 | `<runId>.<kind>.json`（append-only 文件） | config / store 中的结构化字段 |
| 生命周期 | 可删可归档 | 持续演进 |
| 来源 | cosmic-forging §6-2 | 方向性方案 v1.3 §4.8 |

**两者都叫「档案」但不是一回事**——本方案用「测试档案」/「渠道档案」严格区分（对齐 cosmic-forging §6-2 的「命名消歧」要求）。

### 2.2 拆分建议（需确认）

**建议**：本轮只做 **#3 + #4**（补漏 + 统一测试档案），把 **#5 + #6** 拆到下一版。

**理由（三条）**：

1. **#3+#4 是 cosmic-forging 对 v0.9.9 的完整定义**——做完即可宣布「v0.9.9 完成」，有**明确关闭点**。上一次的教训正是「部分交付当完成」，需要一个可判定的终点。
2. **#5+#6 是方向性方案 v1.3 才引入的新规划**，与 #3+#4 无硬依赖（一个存跑批结果，一个存渠道属性）。
3. **#5 含未决问题**：渠道档案的「声明 vs 实测」双轨交互细节（冲突如何呈现、面板如何编辑）尚无设计，需要先定交互再动 schema——否则会重演「schema 引入后又要改」的问题（v1.2 → v1.3 已因维度移除改过一次）。

**若确认拆分，建议命名**：

- 本轮 → **v0.9.9 收口**（不新增版本号，把 v0.9.9 真正做完）
- 下一版 → **v0.9.10「渠道档案与声明通道」**（阶段 A 的剩余部分）

**若不同意拆分**：本方案 §5 的 Task 9/10 已完整规划 #5/#6，可一并执行，但规模从 ~6 任务增至 ~10 任务，且 #5 需先补交互设计。

## 3. 架构决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 落盘命名保持 `<runId>.<kind>.json\|md`，`kind ∈ {model-test, loadtest, probe}` | model-test 已是此格式，**零迁移**；`listRunJson` 的既有后缀扫描逻辑可复用 |
| D2 | 三类档案统一 `schemaVersion: 1`，顶层加 `kind` | 消费端可统一分支；`schemaVersion` 为将来迁移留钩子 |
| D3 | **既有 `.model-test.json` 不回填 `kind`/`schemaVersion`** | 回填需重写全部历史文件，风险大于收益。读取端**按缺失即默认 `kind='model-test'`** 处理（向后兼容） |
| D4 | lister **不引入 meta 索引**，改用**文件级 `stat` + 文件名解析**（零内容读取） | **v1.0 复核修正**：原设计拟引入 `<runId>.<kind>.meta.json`，复核发现**面板历史报告依赖 `list[].targets`**（`client.js:2379` `setSelRun({..., targets: m.targets})`），而新页签只需「按 kind 分组 + 时间倒序」（§6-2 原文），**两者需求不同**。引入 meta 需额外维护一类文件 + 落盘逻辑 + 兼容负担，收益不抵复杂度（Enforce Simplicity）。改为：新端点用 `stat`，旧端点保持现状 |
| D5 | `/model-test/list` **保留为兼容别名**，内部转调同一 lister | 面板与外部脚本可能在用；删端点属破坏性变更 |
| D6 | `runId` 与 `kind` **必须白名单校验** | `/test-archives/detail?kind&runId` 的入参来自 query，**不校验则可路径穿越**（`../../`）。这是本方案唯一的**安全关键点** |
| D7 | 详情视图**复用既有 `ReportView`**（model-test），新增 `LoadtestView` / `ProbeView` | 方案 §5-2 已实现结构化渲染器，不重复造 |
| D8 | 新列/新字段一律**追加**，不改既有列序与子串 | 单测 `test:3102-3104` 断言 `formatReportMarkdown` 含 `\| provider \| model \|` 等子串 |
| D9 | 既有 `ArchiveDrawer` 标题改为「**窗口限额档案** · `<provider>`」 | 避免与「测试档案」歧义（cosmic-forging §6-2 要求） |
| D10 | 落盘失败**不阻塞跑批**（沿用既有 `writeAtomic` + try/catch + warn） | 磁盘问题不应让测试结果丢失（结果仍在内存 + 响应体） |

### Phase 1：补漏（修 P0 缺陷 + 让唯一半成项达标）

#### Task 1a：修复 `normalizeTimeWindows` 放行空 provider/model（**P0，真 bug**）

**Description**：v1.0 复核发现 `lib/config.js` 的 `normalizeTimeWindows` 只校验 `typeof hop.provider === 'string'`，**不校验非空**——`{provider:"", model:""}` 会被放行并进入候选链。

**可达路径**：面板峰/谷候选链编辑器的「+ 添加候选」在 `knownPairs` 为空（registry 未就绪）时，默认值为 `{provider:"", model:""}` → 提交后通过校验 → 保存空 route。

**根因**：`normalizeTimeWindows` 未复用既有的 `checkProviderModel`（`lib/config.js:242`），而 `rules[].route` 走的是它（`config.js:549`）。

> **注**：`checkProviderModel` 做的是**结构校验 + 字段提取**（`provider`/`model` 非空 + 提取 `key`/`quotaGroup`/`tier`），
> **不是** registry 存在性校验。cosmic-forging §九 第 2 条称「provider/model 存在性检查」，表述不准确——
> 但**实质要求成立**：两条路径的校验强度应一致。

**验收判据**：
- [ ] `{provider:"", model:""}` → 抛错（含 `provider` 与 `非空`）
- [ ] `{provider:"p"}`（缺 model）→ 抛错（当前已拒绝，保持）
- [ ] `route` hop 的 `quotaGroup` / `tier` / `key` 字段**仍被保留**（`checkProviderModel` 会提取，确认无字段丢失）
- [ ] 合法 route 的行为**不变**（既有 10 条 v0.9.9 段用例全过）

**验证**：
- [ ] 单测：`{provider:"", model:""}` → `assert.throws(/非空/)`（**红→绿**：先确认修复前该断言失败）
- [ ] 单测：`{provider:"p", model:"m", quotaGroup:"g", tier:"free"}` → 字段保留
- [ ] 全量单测 166 → 168 全绿

**依赖**：无
**文件**：`lib/config.js`
**规模**：**XS**
