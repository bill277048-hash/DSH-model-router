## Critical Issues

### C1. `model-test` 档案落盘仍依赖 `reports.enabled` —— 违反 v0.9.9.3 声明的设计原则

**位置**：
- `lib/model-test.js:260-262`（`get reportDir()`）
- `lib/model-test.js:624-628`（落盘调用点）
- `lib/index.js:254-262`（构造 `ModelTestRunner` 时**未传** `reportDir`）
- `lib/index.js:193`（`daily` 仅在 `cfg.reports.enabled` 为真时创建）

**声明 vs 实现**：

v0.9.9.3 CHANGELOG 与 `lib/archive.js:35-36` 均明确写：

> **不依赖 `reports.enabled`** —— 那是「每日报告」开关，与档案落盘是两回事：
> 用户可能不开每日报告，但仍希望跑批结果落盘可见
> 三类档案（model-test / loadtest / probe）至此**全部落盘**

**实际**：

| 类 | `reportDir` 来源 | `reports.enabled=false`（**默认**）时 |
| --- | --- | --- |
| `probe` | `opts.reportDir` ← `index.js:147` 传 `archiveDir` | ✅ 仍落盘 |
| `loadtest` | `opts.reportDir` ← `index.js:249` 传 `archiveDir` | ✅ 仍落盘 |
| **`model-test`** | `this.daily.reportDir`（**依赖 daily**） | ❌ **静默跳过** |

`index.js:193`：
```js
if (cfg.reports.enabled) {
  daily = new DailyLedger({ ... reportDir: cfg.reports.dir });
}
```
→ `daily` 为 `null` → `modelTest.reportDir` 为 `null` → `lib/model-test.js:626` 走 `log.warn('model-test: daily 报告目录不可用，跳过落盘')`。

**影响**：
1. **默认配置下 model-test 跑批结果静默不落盘**（仅一条 `log.warn`，用户界面无任何提示）
2. v0.9.9.5 新增的「测试档案」页签，对 model-test **恒为空** —— 核心交付物等于没做
3. 「三类档案」只兑现 2/3

**为什么是 Critical 而非 Important**：这不是边缘场景，而是**默认配置**（`reports.enabled` 默认 `false`）；且它使 v0.9.9 的主交付物在默认路径下失效。

**为什么现在没暴露**：实机 `reports.enabled = true`（已实测确认），故 10 个 model-test 档案正常落盘 —— **bug 是潜伏的**，任何用默认配置的用户都会踩到。

**测试缺口**：全库 grep `reports.enabled` 相关断言，**无任何测试覆盖「enabled=false 时 model-test 仍落盘」**。

**建议修复**（3 行）：
```js
// lib/index.js:254
const modelTest = new ModelTestRunner({
  llm, registry, daily, log,
  reportDir: archiveDir,   // ← 新增：与 probe/loadtest 同源
  prompt: 'ping', timeoutMs: 20000,
  threshold: cfg.reports?.modelTestThreshold,
});

// lib/model-test.js:260
get reportDir() {
  return this.reportDir_ || (this.daily && this.daily.reportDir) || null;
}
```
并补一条单测：`reports.enabled=false` 时 `modelTest.reportDir === archiveDir`。

## Important Issues

### I1. `writeAtomic` 丢失 tmp 清理 —— 新实现比被它替换的旧实现更弱

**位置**：`lib/archive.js:56-65`

```js
export function writeAtomic(target, content, log) {
  const tmp = `${target}.tmp-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`;
  try {
    writeFileSync(tmp, content, { encoding: 'utf8', flag: 'wx' });
    renameSync(tmp, target);
  } catch (error) {
    log?.warn?.(`archive 写盘失败 ${target}: ...`);
    throw error;            // ← tmp 文件未清理
  }
}
```

**对照** `lib/daily.js:427-437`（v0.9.9 之前就存在）**有**清理：
```js
} catch (error) {
  this.log.error?.(...);
  try { unlinkSync(tmp); } catch { /* ignore */ }   // ← 有清理
  ...
}
```

**实证复现**（模拟 rename 失败）：
```
写盘抛错（预期）: CODEBUDDY_BROKER_DENY
目录残留: [ 'blocked', 'blocked.tmp-1789642024317-9djz93' ]
⇒ tmp 文件是否残留: ⚠ 是（未清理）
```

**影响**：
1. 反复失败会在用户 `~/Documents/` 累积垃圾文件
2. v0.9.9.2 号称「消除三套重复的原子写实现」，但**新实现丢了 daily 版本已有的清理逻辑** —— 这是重构引入的**功能倒退**

**测试缺陷**：`test('v0.9.9.1: archive——writeAtomic 原子写（tmp 不残留）')` **只覆盖成功路径**：
```js
writeAtomic(target, '{"a":1}', {});
assert.equal(readFileSync(target, 'utf8'), '{"a":1}');
const leftovers = readdirSync(dir).filter((n) => n.includes('.tmp-'));
assert.deepEqual(leftovers, [], '无 .tmp 残留');   // ← rename 成功后 tmp 自然消失，恒真
```
测试名承诺「tmp 不残留」，但**恰好没测真正会残留的失败路径**。

**建议**：`catch` 里补 `try { unlinkSync(tmp); } catch {}`；单测补失败路径断言。

### I2. `startedAt` 同名异义 —— 列表用文件 mtime，详情用报告自身字段

**位置**：
- `lib/archive.js:203`：`startedAt: st.mtime.toISOString()`（**mtime**）
- `lib/routes.js:1110`：`startedAt: raw.startedAt ?? null`（**报告自身字段**）

**消费方**：
- `client.js:2525`（列表行）：`it.startedAt` → 显示 mtime，且该列**无表头标注**
- `client.js:2569`（详情头）：`rep.startedAt` → 显示报告开始时间，标注「开始」

**影响**：
1. 列表按 **mtime** 倒序（文案却写「按时间倒序」）—— 经 `POST /model-test/manual` 重写档案后 mtime 变新，**旧跑批会「跳」到列表顶部**
2. 同一份档案，列表显示的时间与点进详情后显示的时间**不同** → 用户困惑

**建议**：重命名为 `mtime`（列表）/ 保留 `startedAt`（报告），或列表同时返回两者、优先显示报告 `startedAt`。

### I3. 两套时间机制端点语义不一致（`<=` vs `<`）

**位置**：
- `lib/router.js:inTimeWindow`：`t >= hours.start && t <= hours.end`（**含端点**）
- `lib/router.js:segmentOf`：`t >= peakStart && t < valleyStart`（**半开**）

**实证**（peak 09:00→22:00，规则时段窗 09:00-22:00）：
```
t=21:59  规则时段窗命中=true   段=peak
t=22:00  规则时段窗命中=true   段=valley    ← 矛盾
```

**影响**：同时配置 `rules[].hours` 与 `timeWindows` 的用户，在边界分钟会遇到「规则说命中、段说已切换」。

**说明**：两者是独立特性，`<=` / `<` 可能各自有意为之 —— 但**代码与文档均未说明差异**。建议至少补注释明确「这是刻意的」，或在文档中提示用户不要在边界分钟依赖两者一致。

## Suggestions

### S1. `localHHMM` 未显式 `hourCycle: 'h23'`（可移植性隐患）

**位置**：`lib/router.js:localHHMM`
```js
const opts = { hour: '2-digit', minute: '2-digit', hour12: false };
return new Intl.DateTimeFormat('en-GB', opts).format(now);
```

`hour12: false` 而不指定 `hourCycle`，在部分 ICU 实现下会产出 **h24**（`"24:00"` 而非 `"00:00"`），破坏本模块依赖的**字符串比较有序性**。

**实测**：当前 Node 22.22.2 + en-GB 返回 `"00:00"` ✓（无实际 bug），但插件要分发到其他机器。

**若真出现 h24 的错判场景**（peak 22:00→valley 00:00，午夜）：
```
正确 t="00:00" → valley ✓
异常 t="24:00" → peak ✗
```

**单测缺口**：grep `hourCycle` / `24:00` 无任何断言 → 无防护。

**建议**：加一个词 `hourCycle: 'h23'`，并补一条断言 `localHHMM(tz, 午夜) === '00:00'`。

### S2. `lib/routes.js` 函数内 `require()` 与顶部 `import` 混用

**位置**：`lib/routes.js:1099-1100`
```js
const { readdirSync } = require('node:fs');
const { basename } = require('node:path');
```
顶部已有 `import { readFileSync } from 'node:fs'` / `import { join } from 'node:path'`。此处的 `require` 依赖 L102 的 `createRequire` shim（那是为读 `package.json` 而设），**无必要**。

**注**：**不是 bug**（已实测 `require` 由 `createRequire` 提供，可用），纯风格一致性问题。

### S3. 「消除三套重复原子写」的文档声明与事实不符

CHANGELOG v0.9.9.2 表格称 `archive.writeAtomic` 为「**唯一实现**」，但实际仍有 **4 处**独立实现：

| 文件 | 形式 | 是否有 tmp 清理 |
| --- | --- | --- |
| `lib/archive.js:56` | `.tmp-<ts>-<rand>` | ❌（见 I1） |
| `lib/daily.js:427` | `.tmp-<ts>-<rand>` | ✅ |
| `lib/store.js:45` | `.tmp-<pid>` | ❌（自覆盖，不累积） |
| `lib/quota.js:392` | `.tmp-<pid>` | ❌（自覆盖，不累积） |

**建议**：修正文档表述（scope 到「档案落盘」），或真做统一（`store`/`quota` 用确定名自覆盖，可保留）。

### S4. 两套档案列表器并存，`/model-test/list` 仍读全文

- `listRunJson`（`routes.js:1097`，读全文，为兼容 `list[].targets`）
- `listArchives`（`archive.js:189`，只 `stat`，三类通用）

有文档说明兼容原因 ✓。但 `/model-test/list` 每次读全文（实测 9 文件 168KB 需 466ms），面板轮询会浪费 IO。

**建议**：中期把 `targets` 摘要做进轻量 lister，让两条路径合一。

## What's Done Well

1. **路径穿越加固（v0.9.9.4）质量最高**：`assertSafeRunId`（格式白名单 + `..` 显式拒绝 + 长度上限）**+** `safeArchivePath`（`resolve` 归一化后前缀确认）**双防线**。注释写明了攻击场景（`runId="../../../tmp/evil"` → 任意文件写）与「第二道防线即使第一道被绕过也能兜住」的设计意图 —— 这是我在本次审核中见到的最高水准的一处。

2. **`kind` 校验双向闭环**：`archiveName`（写入侧）与 `kindOfFilename`（读取侧）都走 `ARCHIVE_KINDS` 白名单，非法 kind 双向拒绝。

3. **`listArchives` 有实测依据**：用 `stat` 而非读全文（实测 466ms → 0ms），并正确处理「单文件 stat 失败跳过」+「目录不存在返回空」两类容错 —— 没有让旁路功能拖垮主流程。

4. **`segmentOf` 时段逻辑严谨**：半开区间拼接完整 24 小时，**无重叠无缝隙**；且 `peakStart === valleyStart` 由 config 层前置校验（我核对了 router 注释的声明与 config 实现，**一致**）。

5. **`persistReport` 失败返回 `null` 不阻塞跑批** —— 符合「落盘是旁路」的正确定位。

6. **向后兼容有考虑**：旧档案无 `kind` → 读取端回退 `'model-test'`。
