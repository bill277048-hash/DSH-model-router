## 1. 背景与问题定义

### 1.1 使用场景

DSH（DeepSeek Harness）允许用户同时装配**多个模型供应商**（provider）——既包括官方渠道，也包括第三方网关；同一平台还可以通过**多个 API Key** 注册为多个独立 provider。实机当前已装配 **39 个 provider**，其中 `apikey-202606301659`、`apikey-202608290333` 即典型的「同平台多账号」形态。

这些渠道的可用性、速率上限、配额窗口、上下文容量**各不相同且随时变化**；而 DSH 的调用侧（agent loop）只认识「一个模型」，不感知底层由哪个渠道承载。

### 1.2 核心矛盾

> **供给侧的异构、易变、不透明** ⟷ **需求侧的稳定、连续、无感**

具体表现为五类问题：

1. **可用性断裂**：某个渠道 401/429/超时，若直接暴露给 agent loop，表现为「对话失败」。
2. **限制不透明且多维**：各家的 5 小时 / 周 / 月窗口额度、重置时点、RPM 上限、TPM（tokens per minute）上限、上下文容量各不相同，用户无法从文档准确获知，只能试错。**更麻烦的是限制维度之间存在耦合**——实测（ST-rrx / ST-rrx199 渠道的 `deepseek-v4-flash`）显示：`context` 相在 1024 通过、8192 触发 `RATE_LIMIT`，上游错误消息为 `inference exceeds tpm/rpm limit`。**直接机制是 TPM 消耗，而非「上下文长度」本身**——上下文越长，单次请求消耗 token 越多，TPM 额度耗尽越快。这意味着「RPM 达标」并不等于「这个请求能成功」。
3. **配置负担**：插件当前的限额信息依赖**手工声明**（`config.providerMeta`）。实机该字段**为空**——用户不填，插件就只能「盲跑」；而新渠道接入时自动判断恰恰最难（无历史样本，主动测试又耗额度）。
4. **失败不可归因**：一次调用失败，用户看到的是错误码，无法判断是「凭据问题」「速率限流」「上下文过长导致限流」还是「网络抖动」。
5. **宣称值与实际值不符**：部分平台对外宣称的限额与实际可用限额不一致，使得「照文档配置」也不可靠。

### 1.3 问题定义

本方案要解决的核心问题可归纳为一句话：

> **如何让插件在没有人工持续干预的前提下，自主完成「发现资源 → 判断能力 → 编排使用 → 修复异常 → 保持更新」的闭环，使调用侧获得一个稳定、连续、可解释的模型服务面。**

## 2. 最终目标

### 2.1 愿景陈述

**把插件建设为一个自适应、可自愈、可解释的多渠道模型调度层。**

它对外表现为「一个稳定模型」，对内持续完成五件事：

| 能力 | 一句话定义 |
| --- | --- |
| **自动识别** | 无需人工登记，自动发现可用 provider、模型与其变更 |
| **自动判断** | 通过针对性测试与历史记录，推断各渠道的真实使用限制 |
| **自动排布** | 按时段、配额、健康度自动编排候选链，选择「当下最合适」的渠道 |
| **自动修复** | 失败自动切换、熔断、恢复试探，无需人工介入 |
| **自动更新** | 插件自身可升级、配置可迁移，不依赖手工覆盖文件 |

四项支撑要求：

- **多平台多账号接入**：把异构渠道统一为同构的「可调度资源池」
- **使用限制准确判断**：从「手工声明」转向「实测推断 + 人工校正」
- **记录结构化**：所有观测数据统一 schema，可关联、可提取关键信息
- **客户端无感知**：切换与调度对 agent loop 透明，不改变调用侧行为

### 2.2 可度量目标

| 维度 | 现状（v0.9.8） | 目标 |
| --- | --- | --- |
| 新渠道接入可用性 | 需手工填 `providerMeta`，但结构简单、无校正机制 | **声明即可用**：接受用户依说明文档声明的限额/重置规则，立即投入排布；自动观测持续校正 |
| 单点失败影响 | 已可无感切换（首分片前） | 保持；并将「自动移出/恢复候选」纳入闭环 |
| 限额判断来源 | 手工声明为主，且不留存 | **声明与实测双轨**，实测优先排布、声明保留对照，冲突可见 |
| 限制维度覆盖 | 速率 / 容量 / 配额 / 恢复 | 增加**「上下文 × 限流」耦合**维度，并支持事前分流规避 |
| 失败归因 | 需人读报告判断 | 报告**自动给出分类结论**（凭据 / 速率限流 / **上下文限流** / 下架 / 网络） |
| 升级方式 | 手工 `cp` + `launchctl kickstart` | **自动化**：安装 → 升级 → 回滚有明确机制 |
| 观测数据一致性 | 四套记录彼此独立 | **统一 schema + 关联键 + 渠道档案**，可跨源关联 |

## 3. 范围

### 3.1 在范围内

- provider / 模型 / 账号的自动发现与变更追踪
- **用户声明通道**：新渠道接入时可依说明文档声明限额、重置规则、来源等，声明即可投入排布
- 使用限制的多维推断（速率 RPM、上下文容量、配额窗口、重置时点、**上下文 × 限流耦合**）
- 声明值与实测值的**双轨对照与冲突标注**
- 候选链的自动编排（时段、配额、健康度、**上下文规模**四类输入）
- **上下文预判分流**：请求前估算输入长度，超过渠道阈值时提前改道（避免触发限流）
- 失败的自动切换、熔断与恢复
- 观测记录的统一 schema、**渠道档案**与关键信息提取
- 插件的升级与配置迁移机制
- 面板与诊断能力（服务于上述能力的可解释性）

### 3.2 不在范围内（明确不做）

| 项 | 理由 |
| --- | --- |
| 代理 / 转发上游请求 | 插件只做**路由与调度**，不介入协议转换；不读、不存、不转发 API Key |
| 自动申请 / 购买额度 | 属用户决策 |
| 自动修改上游账号配置 | 越权且不可控 |
| 任意时段列表 / 多窗口叠加 | 峰谷两段已足够覆盖典型作息；复杂度收益比过低 |
| 模型输出质量评估 | 属模型能力评估，非路由职责；插件只判断**可用性**与**限制** |
| **按上下文长度做质量降级** | 上下文预判分流的目的是**规避限流**，不是「长文本自动换小模型」。不因输入长就降低模型档位——那是质量决策，须由用户显式表达 |
| **对同一会话中途改换上下文相关策略** | 首分片后不可切换（文法约束）；上下文分流只作用于**请求发起前** |
| 并发化跑批 | 与 `recoveryMs` 冷却语义冲突，会污染限流测量 |
| 对确定性错误（401/400）自动重试 | 重试无意义，只会拖长失败路径 |
| 硬编码上游阈值 | 长上下文触发限流的机制尚待验证，阈值**必须来自该渠道实测/观测**，不得内置猜测值 |

## 4. 核心能力设计

> 每项能力给出**目标状态**、**关键设计**、**当前基线**三部分，便于对照实施。

### 4.1 自动识别（Auto-Discovery）

**目标状态**：插件启动后无需人工登记，即可获得「有哪些 provider、各有哪些模型、何时发生变化」的完整视图；变更（新增渠道、模型上下架）可被感知并记录。

**关键设计**

1. **资源来源单一化**：只从 DSH 自身的 provider 注册表发现，不引入第二套登记入口（避免双源漂移）。
2. **周期性刷新 + 变更检测**：定期拉取，比对上一次快照，产出「新增 / 消失 / 变化」三类事件。
3. **变更事件驱动后续动作**：新增渠道 → 排队探测；模型消失 → 从候选链移除；这使识别不止于「看见」，而能触发下游。
4. **多账号同构化**：同一平台的不同 API Key 注册为独立 provider，插件对其一视同仁——这是「多账号」支持的实现基础。

**当前基线**

- 已实现：`Registry.refreshProviders()` / `refreshModels()` / `registeredPairs()` / `isKnownProvider()` / `isKnownModel()`（`lib/registry.js:102/153/185/211/216`）
- 已具备多账号形态（实机 39 个 provider 含 `apikey-*`）
- **差距**：刷新是周期性的，但**无变更事件产出**，下游无法据此触发探测或清理。

### 4.2 自动判断（Auto-Assessment）

**目标状态**：插件给出每个渠道的可用性画像与使用限制估计，并标明每项的**来源与置信度**；刚接入的渠道在自动观测积累之前，可依据用户声明立即投入可用。

**关键设计**

1. **三类来源，各有分工**（关键：不假定「自动一定优于声明」）：

   | 来源 | 适用时机 | 特点 | 局限 |
   | --- | --- | --- | --- |
   | **声明**（用户提供） | **刚接入时立即生效** | 零成本、可含文档中的明确信息（如官方限额、重置规则） | 可能虚标；部分平台**宣称值与实际值不符** |
   | **实测**（主动测试） | 按需触发 | 直接测出边界，最接近真实 | 消耗额度；样本少时置信度低 |
   | **观测**（历史记录） | 持续积累 | 零成本、覆盖真实使用模式 | 覆盖面取决于使用习惯；冷启动期无数据 |

2. **默认路径是「先声明，后校正」**：新渠道接入时自动判断难度最高（无历史样本、主动测试又耗额度），此时**必须支持用户依据说明文档手工声明**，插件据此立即排布；随后由使用记录持续校正。**不把「等自动测出来」作为唯一路径。**

3. **推断规则集中化**：把「从错误码推断是哪个窗口耗尽」「从 429 响应学习重置时点」等规则集中管理，便于调参与审计。

4. **冲突时双轨保留，不静默覆盖**：声明与实测不一致时，**两者并列展示并标注差异**，实测优先用于排布、声明保留可查。理由：宣称值与实际值不符是常见现象，而单次实测也可能受瞬时因素影响——**任何一方都不应单方面抹掉另一方**。

5. **置信度表达**：样本量不足时标注低置信，避免「一次成功 = 该渠道健康」的误判。置信度应随样本数增长而提升，并在面板可见。

**当前基线**

- 已实现推断雏形：
  - `deriveWindowId(code)` —— 从错误码推断是 5 小时窗还是周窗（`lib/quota.js:26`）
  - `WindowLedger.markReset(provider, windowId, meta, resetAt)` —— **从上游响应学习重置时点**（`lib/quota.js:239`）
  - `computeTrmBound(ladder, safety)` —— 从 RPM 实测阶梯推算上限（`lib/probe.js:219`）
  - `ProbeBoard.runProbe/runAll` —— 主动探测（`lib/probe.js:136/189`）
- 已实现声明通道：`config.providerMeta` 支持声明 `quotaGroup` / `tier` / 窗口限额
- **差距**：
  1. 推断结果**不写回**配置（实机 `providerMeta` 为空），即「能推断但不留存」，下次启动又从零开始
  2. 声明与实测**无对照机制**——既不知道两者是否一致，也不保留差异
  3. 声明结构过于简单（仅 `quotaGroup` / `tier` / 窗口），不足以承载「重置规则」「上下文限制」等文档中的信息

### 4.3 自动排布（Auto-Scheduling）

**目标状态**：候选链由插件按「时段 + 配额 + 健康度 + **上下文规模**」自动编排，用户只需表达偏好（如「白天用 A、夜间用 B」）。

**关键设计**

1. **四层输入**：
   - **时段**：峰/谷两段各一套完整候选链（极简两段制，不做任意时段列表）
   - **配额**：窗口剩余额度不足的渠道自动降权或跳过
   - **健康度**：处于熔断或近期失败的渠道自动后置
   - **上下文规模**（本次需求新增）：**请求前估算输入长度，若预计超过某渠道的限流阈值，提前改道**——不等 429 发生。这是唯一可主动规避的限流类型（见 4.7 第 2 点）。
2. **排布结果的可见性**：面板必须能回答「此刻为什么选它」，否则自动排布会变成不可调试的黑盒。上下文分流尤其需要可见——否则用户会困惑「为什么同样的问题，长文档走了另一个模型」。
3. **边界纪律**：显式的用户选择（绑定规则、指定模型包）**优先于**全局自动策略。
4. **段不影响会话种子之外的语义**：切换仍只能在首分片前发生，排布不改变流式文法约束。
5. **分流的保守性**：上下文估算基于字符/token 近似，**存在误差**。分流阈值应留安全余量，且**估算失败时退回默认候选链**（宁可冒 429 风险，也不因估算错误而拒绝服务）。

**当前基线**

- 已实现：静态规则链 `rules` + 按序尝试 + `fallbackPolicy.maxRetries`；`cooldown` 熔断后自动跳过失败渠道
- 已规划（v0.9.9）：`timeWindows` 峰谷两段，段链路在 `matchRule` 返回处统一收口
- **差距**：配额与健康度**尚未参与排布**——当前只是「熔断时跳过」，不是「按剩余额度与健康度排序」。

### 4.4 自动修复（Auto-Recovery）

**目标状态**：异常发生与恢复都无需人工介入，且恢复过程可观测。

**关键设计**

1. **失败切换**：首分片前收到可切换错误码 → 立即改走候选链下一项（对调用侧无感）。
2. **熔断与恢复试探**：连续失败达阈值 → 进入熔断；冷却后放行试探，成功即自动回归。
3. **配额感知的差异冷却**：配额类错误冷却时间显著长于瞬时错误（配额不会在短冷却内恢复）。
4. **确定性错误的快速失败**：凭据类错误不重试、直接短路后续测试相，避免白耗。
5. **升级路径**：从「短时熔断」扩展到「连续失败的渠道自动移出候选池，并在后续探测成功后自动回归」——这需要 4.1 的变更事件与 4.2 的推断结果共同支撑。

**当前基线**

- 已实现：`wrapper` 首分片前 failover（`lib/wrapper/index.js`，808 行，插件最核心的部分）；`cooldown` 熔断（`lib/cooldown.js`）；`fallbackPolicy` 中 `failureThreshold` / `cooldownSec` / `quotaFailureThreshold` / `quotaCooldownSec` 差异化配置；`failoverSignals` 错误码表（v0.6.0 已对齐实机错误码）
- 已实现（v0.9.8）：probe 相退避重试（仅瞬时错误）、短路表（凭据类全停）
- **差距**：无「自动移出候选池」与「自动回归」；熔断是时间维度的，不是成员维度的。

### 4.5 自动更新（Auto-Update）

**目标状态**：插件的安装、升级、回滚有明确机制，配置结构变更可自动迁移。

**关键设计**

1. **配置 schema 版本化**：配置与落盘数据都带 `schemaVersion`，升级时按版本链迁移，而非「字段缺失就回退默认」。
2. **升级路径不依赖手工文件操作**：当前升级需要手工覆盖 `node_modules` 并重启守护进程，属交付环节的稳定性缺口。
3. **向后兼容承诺**：明确的「废弃策略」——旧字段在若干版本内保留并告警，而非静默丢弃。
4. **回滚能力**：升级失败可回到上一版本，且配置不因回滚而损坏。

**当前基线**

- 落盘侧：`store.js` 已有 `version: 1` 校验（格式不符则忽略并沿用默认，`lib/store.js:15`）
- **差距（本方案最大缺口）**：**无升级机制、无配置迁移链**。实机部署依赖手工 `cp` + 改 profile `package.json` + `launchctl kickstart`；`store.js` 白名单仅含 `propose` / `rules` / `providerMeta` / `reports`，已导致 `timeZone` / `mode` 持久化断链（配置改动重启即丢）。

### 4.6 多平台多账号接入

**目标状态**：任意数量的平台与账号，以同构方式纳入资源池，无需为每个平台编写适配逻辑。

**关键设计**

1. **不新增接入层**：沿用 DSH 既有的 provider 机制，插件只消费其注册表。这保证了「插件不读 API Key」这一安全边界——密钥管理始终在 DSH 侧。
2. **账号级隔离**：同一平台的不同账号是**独立可调度单元**（可独立设置配额、健康度、优先级），而非「一个平台的多个端点」。
3. **跨账号的配额组**：支持声明「这些账号共享同一配额池」，使插件能把它们当作一个整体计量——这是免费额度场景的关键。

**当前基线**

- 已实现：provider 级别的完整支持；`providerMeta.quotaGroup` 已支持跨 provider 的配额组声明；`model-test` 的 `quota-group` 相可探测同组成员
- **差距**：`quotaGroup` 需手工声明（实机为空）；无「同一平台多账号」的自动归组。

### 4.7 使用限制的准确判断

**目标状态**：对每个渠道给出**多维**限制画像，且每项标明来源（声明 / 实测 / 观测）与置信度；限制维度之间**允许耦合**（如上下文长度影响限流触发），并把可事前预判的限制用于提前分流。

**关键设计**

1. **限制是六维的，不是一维的**：

   | 维度 | 含义 | 可事前预判 | 主要获取方式 |
   | --- | --- | --- | --- |
   | 速率（RPM/QPS） | 单位时间可发起的**请求数** | 否（只能事后反应） | RPM 阶梯实测 |
   | **吞吐（TPM）** | 单位时间可消耗的 **token 数** | **是**（可估算本次 token 量） | 由 429 错误消息反推 + 定向测试 |
   | 容量（上下文 token） | 单次请求可接受的输入长度上限 | **是**（可估算 prompt 长度） | 上下文二分探测 |
   | 配额（窗口额度） | 5h / 周 / 自定义窗口的可用量 | 部分（剩余量已知） | 上游响应学习 + 用量累计 |
   | 恢复（重置时点） | 窗口何时重置 | 部分 | 从 429 响应学习 + 声明 |
   | **耦合（上下文 × TPM）** | **上下文越长 → 消耗 token 越多 → 越易撞 TPM 上限** | **是**（可估算后分流） | 观测统计 + 定向测试 |

   > **TPM 是「上下文越容易触发限流」的根本解释**。实机证据见下文第 2 点：上游错误消息明确为
   > `inference exceeds tpm/rpm limit`，而非「输入过长」。因此档案应记录 **TPM 限制**这一根本量，
   > 「上下文阈值」只是它在特定使用模式下的表现。

2. **「上下文 × 限流」耦合必须独立建模**（本次需求新增）：

   **案例渠道（已核实）**：

   | 代号 | 实机 provider | 模型数 | 归属 |
   | --- | --- | --- | --- |
   | ST-rrx | `apikey-202606301659` | 3（`deepseek-v4-flash` / `glm-5.2` / `kimi-k3`） | 商汤科技，`settingsNs: llm-pi-ai` |
   | ST-rrx199 | `apikey-202608290333` | 2（`deepseek-v4-flash` / `glm-5.2`） | 同上 |

   > 两渠道合计 5 个模型（`deepseek-v4-flash` / `glm-5.2` 两渠道各有，`kimi-k3` 仅 ST-rrx），
   > 与用户描述的「来自 ST / ST199 的 5 个模型」一致。**注意：模型在两个渠道间有重叠**，
   > 因此「5 个模型」是 5 个 `(渠道, 模型)` 组合，而非 5 个不同模型。

   **实机实测证据**（`model-test` 报告 `2026-09-16T00-46-57-oqdp`，v0.9.8 已带 `errorMessage`）：

   | 目标 | rpm 相 | context 相 | 上游错误消息 |
   | --- | --- | --- | --- |
   | ST-rrx / `deepseek-v4-flash` | lastOkRpm=0.2, first429=0.3 | **1024 ✓ / 8192 ✗ RATE_LIMIT** | `inference exceeds tpm/rpm limit`（code `429001`）<br>`rpm exhausted`（`quota_exceeded_error`, code `8`） |
   | ST-rrx199 / `deepseek-v4-flash` | lastOkRpm=0.05, first429=0.1 | **1024 ✓ / 8192 ✗ RATE_LIMIT** | `inference exceeds tpm/rpm limit`（code `429001`） |
   | ST-rrx / `kimi-k3` | probe 相即 FAIL | — | `ModelAccountTpmRateLimitExceeded` |
   | 两渠道 / `glm-5.2` | lastOkRpm=0.3 | 8192 ✓ 全通过 | — |

   **机制结论（由上游错误消息揭示，非猜测）**：

   - 直接机制是 **TPM（tokens per minute）**，而非「上下文长度」本身。上下文越长 → 单次请求消耗 token 越多 → **TPM 额度消耗越快** → 越容易撞上限。这解释了「上下文超过 100k 时 429 概率上升」的观察。
   - 上游返回的 429 **至少分三类**，必须分开归因：

     | 类别 | 特征 | 恢复方式 |
     | --- | --- | --- |
     | TPM/RPM 速率限制 | `inference exceeds tpm/rpm limit`、code `429001` | 短时等待即可恢复 |
     | 配额耗尽 | `rpm exhausted`、`quota_exceeded_error`、code `8` | 需等窗口重置 |
     | **账号级** TPM 限制 | `ModelAccountTpmRateLimitExceeded` | 账号维度，**换模型也无效** |

   - **问题集中在 `deepseek-v4-flash`**：同一渠道的 `glm-5.2` 未复现（8192 全通过）。因此「ST 渠道整体有问题」的说法不准确——**耦合是「渠道 × 模型」级别的属性**，不能按渠道一概而论。

   **实测局限（必须如实标注）**：

   - 上述为**合成 prompt 的测试数据**，非真实使用数据；daily 记录中**暂无** ST 渠道的真实调用样本（近 3 日 82 条记录中 0 条）。
   - 测试相之间存在**累积影响**：`rpm` 相（最多 4 档 × 5 样本）先跑完并消耗了 TPM，`context` 相后跑，因此「8192 失败」未必是 8192 上下文本身所致，可能是 TPM 已被前序相消耗。
   - 当前 `context` 相仅 1024 / 8192 两档，**无法定位 100k 量级**，也无法验证「100k 是阈值」这一具体数值。

   **建模方式**：

   - 档案应记录**根本量（TPM 限制）**，而非仅记录「上下文阈值」：
     `contextThrottle: { tpmLimit, thresholdTokens, samples, hitRate, confidence }`
   - **「上下文预判分流」的判据**：预计本次请求 token 数 × 近期已消耗 TPM 是否超该渠道上限——而非简单地「长度 > 某阈值就改道」。
   - **为什么这条比 RPM 限流更重要**：RPM 限流**只能事后反应**（已经 429 了才切换）；而**请求的 token 量可在发起前估算**，因此可以**提前改道**——这是唯一一个「可主动规避」的限流类型。
   - **机制细节待验证**：除 TPM 外，是否还存在「长输入独立速率约束」「账号级与模型级限制的叠加」等，需更多样本验证。**在验证之前不写入任何硬编码阈值**——阈值必须来自该渠道的实测/观测数据。

3. **声明与实测的双轨机制**（本次需求新增）：

   - 新渠道接入时**优先接受用户声明**（说明文档通常写明官方限额与重置规则），使插件立即可用；
   - 使用过程中持续用观测数据校正，**宣称值与实际值不符时以实测为准排布，同时保留声明并标注差异**；
   - 声明结构需能承载文档信息：限额数值、重置规则（如「滚动 5 小时」「每周一 00:00」）、来源链接、更新时间。

4. **主动测试与被动观测互补**：主动测边界（成本高、准确、按需），被动持续采样（零成本、覆盖面取决于使用模式）。

5. **关键信息的自动提取**：从上游错误消息与响应头中提取「限额数字」「重置时间」「限流原因」，而不是只留一个错误码。

6. **避免误判**：凭据类失败（401/403）**不得**被计入限流统计——实机曾出现「54 个目标全失败被误读为限流」，根因正是未区分错误类别。同理，上下文导致的 429 与速率导致的 429 也应分开归因。

**当前基线**

- 已实现：四相测试（`probe` / `rpm` / `context` / `quota-group`）；RPM 阶梯测量；上下文容量二分探测（`CONTEXT_SIZES = [1024, 8192]`）；`deriveWindowId` 窗口推断；`markReset` 重置时点学习；`computeTrmBound` 上限推算；v0.9.8 起错误消息端到端透传（`errorMessage`）与凭据类黄条提示
- **差距**：
  1. 推断结果**不留存、不写回**
  2. **无「上下文 × 限流」耦合维度**——当前上下文相只测「能否接受」，不测「接受后是否更易触发限流」
  3. 上下文探测粒度粗（仅 1024 / 8192 两档），无法定位 100k 量级的阈值
  4. 「关键信息提取」止于错误消息透传，未做结构化抽取（如从消息中解析限额数值）

### 4.8 记录结构化与关键信息识别

**目标状态**：所有观测数据（调用记录、探测结果、报告、配额状态）共享统一 schema 与关联键，支持跨源关联查询与关键信息提取。

**关键设计**

1. **统一 schema**：落盘文件统一命名与顶层字段（`kind` / `schemaVersion` / `runId` / 时间戳 / 结果），使三类测试结果可被同一套读取逻辑消费。

2. **关联键**：调用记录与探测记录共享可关联的标识（会话、请求链、目标），使「这次失败」能回溯到「该渠道当时的健康度」。

3. **渠道档案（Channel Profile）——「声明 / 实测 / 冲突」三层结构**（本次需求新增）：

   档案是「限制判断」的沉淀载体，也是声明与实测双轨的落地形态：

   ```js
   channelProfile: {
     // ① 声明层：用户提供（来自说明文档），接入即可用
     declared: {
       source: "https://.../limits",          // 来源可追溯
       updatedAt: "2026-09-16T...",
       rpm: 60,
       tpm: 200000,                           // tokens/min（说明文档通常标注）
       contextMax: 128000,
       windows: {
         fiveHour: { limit: 200, resetRule: "滚动 5 小时" },
         weekly:   { limit: 1000, resetRule: "每周一 00:00" },
       },
       contextThrottleHint: null,             // 说明文档若提及长上下文限制则填此
     },
     // ② 实测层：自动观测/主动测试积累，带置信度
     observed: {
       rpm: 0.3,
       tpm: null,                             // 由 429 消息反推；未知时为 null
       contextMax: 8192,
       contextThrottle: {                     // 上下文 × TPM 耦合
         tpmLimit: null,                      // 根本量（优先记录）
         thresholdTokens: 8192,               // 表现量（特定使用模式下的阈值）
         samples: 12,
         hitRate: 0.67,
         confidence: "medium",
       },
       // 429 分类计数——区分三类，避免归因混淆
       throttleClasses: {
         rateTpmRpm: 3,                       // inference exceeds tpm/rpm limit（429001）
         quotaExhausted: 1,                   // rpm exhausted / quota_exceeded_error（code 8）
         accountTpm: 0,                       // ModelAccountTpmRateLimitExceeded
       },
       windows: { fiveHour: { limit: 200, used: 143, resetAt: "..." } },
       sampleCount: 340,
       lastUpdated: "2026-09-16T...",
     },
     // ③ 冲突层：宣称与实际不符时可见，不静默覆盖
     conflicts: [
       { field: "rpm", declared: 60, observed: 0.3,
         note: "宣称 60 RPM，实测在 0.3 QPS 即出现 429" },
       { field: "contextThrottle", declared: null, observed: { thresholdTokens: 8192 },
         note: "说明文档未提及长上下文限制，实测 8192 档即触发 TPM 限流" },
     ],
   }
   ```

   **设计要点**：
   - **三层都保留**，任何一方都不单方面抹掉另一方
   - 排布**以 `observed` 为准**（更接近真实），`declared` 作为冷启动依据与对照基线
   - `conflicts` 是**面板与报告的显式展示项**——让「平台虚标」这件事被看见，而非埋在日志里
   - **字段一次设计到位**：档案 schema 应在引入时即包含 `contextThrottle` 与三层结构，避免后续为加维度而升级 `schemaVersion`（迁移成本高）

4. **三类记录的分工**：
   - **调用记录**（每次真实调用）：回答「发生了什么」
   - **探测记录**（主动测试）：回答「能力边界在哪」
   - **聚合报告**（按日/按批）：回答「趋势与归因」
   - **渠道档案**（跨时间累积）：回答「这个渠道到底是什么脾气」

5. **关键信息提取**：从原始记录中提炼出可直接决策的结论——例如「失败率最高的渠道」「限额最紧的渠道」「错误类型分布」「哪些渠道在长上下文下不可靠」——而非让用户读原始日志。

6. **保留原始层**：结构化视图之外，**必须保留原始记录可查**（审计与排障需要）。

**当前基线**

- 已实现：每日调用记录落 NDJSON（`daily.recordCall` → `{day, ts, ...rec}`，异步 flush）；内存环形缓冲（`metrics` ring，容量 200，快照取末 50）；跑批报告落 json + md；配额状态落盘
- 已实现（v0.9.8）：`seqId` / `prevProvider` / `prevModel` / `switched` 字段，使「同一请求链的多次尝试」可分组（这是**关联键的起点**）
- 已规划（v0.9.9）：落盘统一 `kind` + `schemaVersion`，新增 `/test-archives` 端点与「测试档案」页签
- **差距**：四套记录**仍彼此独立**（调用记录 / 探测记录 / 报告 / 配额状态无统一 schema）；无跨源关联；无自动化的关键信息提取（归因仍需人读报告）。

### 4.9 客户端无感知

**目标状态**：所有调度行为对 agent loop 透明——调用侧只感知「一次正常的流式响应」，不感知切换、熔断、重试。

**关键设计**

1. **包装层而非替换层**：通过 DSH 的 `llm/stream` waterfall 介入，首选请求原样透传，行为与无插件时一致。
2. **流式文法硬约束**：切换**只能在首分片之前**发生（commit-on-first-chunk）。首分片之后绝不切换——这是保证下游不收到残缺流的根本约束，任何调度能力都不得突破。
3. **失败也要保文法**：候选耗尽时合成合法的 error finish（保留真实错误码），而不是中断流。
4. **面板操作不干扰调用路径**：面板的读写、测试跑批都不得阻塞或污染正常调用（`recoveryMs` 冷却、探测标记等机制即为此设计）。
5. **能力边界要写清**：明确「哪些情况可以无感」「哪些不能」（如首分片后的失败无法切换），避免对「无感知」的过度承诺。

**当前基线**

- 已实现：`llm/stream` waterfall 包装；首选原样 `next()` 透传；首分片前 failover；看门狗超时切换；候选耗尽合成 error finish；`propose: false` 时对会话模型选择零干预；探测/压测路径与正常调用隔离（标记区分，零污染）
- **差距**：无（核心已达成）；需要的是**把边界文档化**，并保证后续自动排布不越界。

- 统一测试档案：落盘统一 `kind` + `schemaVersion`；`loadtest` / `probe` 结果落盘；`/test-archives` 端点与「测试档案」页签
- **渠道档案 schema 一次到位**：引入 `declared` / `observed` / `conflicts` 三层结构，并**预置 `contextThrottle` 字段**（即便 v0.9.9 尚不填充），避免后续为加维度升级 `schemaVersion`
- **声明通道扩能**：`providerMeta` 从当前的 `quotaGroup` / `tier` / 窗口，扩展到可承载「重置规则」「来源链接」「上下文限制提示」
- 补 `pickPrimary` 在段启用时的不变式断言

**阶段目标**：时段可配、档案可查、**声明可用**（新渠道接入即可投产，不依赖自动探测）。

### 阶段 B：v1.0.0（契约冻结与交付收口）

**主题**：**不加新功能**，把已有能力变成可信赖的稳定契约。

1. **契约文档化**：`/api/model-router/*` 端点、config schema、落盘格式（含渠道档案）三类契约显式文档化，并标注「稳定 / 实验」
2. **配置 schema 版本化与迁移链**：新增字段可迁移，修复 `timeZone` / `mode` 持久化断链
3. **升级/回滚机制**：安装、升级、回滚不依赖手工文件操作
4. **集成测试**：真跑一次跑批的端到端用例 + API 契约断言（当前仅 154 项单测）
5. **多 provider 段场景实机验证**：段合成规则的边界、落盘格式向后兼容
6. **前端可维护性**：`client.js` 单文件已 2388 行，需建立模块边界（这是当前改动风险的主要来源）
7. **安全边界测试化**：「不读 API Key」由测试守住，而非仅写在文档里

**阶段目标**：对外契约稳定，交付自动化。

### 阶段 C：v1.x（数据驱动）

**主题**：把「推断结果」真正接入闭环。

1. **推断结果写回**：实测值自动写入渠道档案 `observed`，与 `declared` 形成对照；冲突写入 `conflicts` 并在面板可见
2. **TPM 推断与上下文预判分流**：从 429 错误消息反推渠道 TPM 上限；请求前估算本次 token 量，结合近期 TPM 消耗决定是否改道（可主动规避的限流类型）
3. **429 三类归因**：按错误消息与 code 区分 TPM/RPM 速率限制（`429001`）、配额耗尽（`quota_exceeded_error`）、账号级 TPM（`ModelAccountTpmRateLimitExceeded`），并据此选择恢复策略（短时等待 / 等窗口重置 / 账号维度处理）
4. **上下文阈值探测**：扩展上下文相的粒度（当前仅 1024 / 8192 两档），支持定位 100k 量级；**隔离相间 TPM 干扰**（如 context 相独立跑，或记录相间 TPM 消耗以修正判读）
5. **成员维度的自动修复**：连续失败的渠道自动移出候选池，探测成功后自动回归
6. **归因自动化**：报告直接给出分类结论（凭据 / 速率限流 / **TPM 限流** / 配额耗尽 / 下架 / 网络）
7. **关键信息提取**：从记录中提炼决策级结论（最紧限额渠道、最高失败率渠道、**长上下文下不可靠的渠道**、错误类型分布）
8. **跨源关联查询**：调用记录与探测记录可按目标/时段关联

**阶段目标**：从「手工配置 + 手工归因」转向「自动推断 + 自动归因」。

## 7. 预期成效

| 受益方 | 成效 | 度量方式 |
| --- | --- | --- |
| 终端用户 | 无需理解渠道差异即可稳定使用；失败不再表现为对话中断 | **新渠道声明即可投产**（不依赖先跑探测）；单渠道故障对调用侧不可见 |

| 维护者 | 升级与回滚可控 | 升级不依赖手工文件操作；回滚不损坏配置 |
| 集成方 | 契约稳定，可安全依赖 | 端点 / 配置 / 落盘（含渠道档案）三类 schema 有文档与版本号 |

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **上游行为不可控** | 渠道可能变更限流策略、下线模型、调整错误码 | 错误码映射集中管理；断言基于行为而非固定错误码表 |
| **主动测试消耗额度** | 跑批会真实消耗免费额度 | 仅按需触发；默认保守参数；测试路径与正常调用隔离 |
| **推断结果误判** | 错误的限额推断会误导排布 | 标注置信度与来源；实测与声明冲突时两者并列展示；不静默覆盖 |
| **上下文 × 限流耦合的量化阈值未知** | 现象已复现（`deepseek-v4-flash` 在 8192 档触发 RATE_LIMIT），但**具体阈值未知**：当前探测粒度仅 1024/8192，无法定位 100k 量级；且测试相之间存在 TPM 累积影响，「8192 失败」未必是 8192 本身所致 | **不硬编码任何阈值**；阈值仅来自该渠道的实测/观测；提升探测粒度并**隔离相间干扰**（如 context 相独立跑、或记录相间 TPM 消耗）；分流策略保持保守（只做规避，不做降级） |
| **429 的归因混淆** | 上游 429 至少三类（TPM/RPM 速率、配额耗尽、账号级 TPM），混为一谈会导致错误的恢复策略（如把「需等窗口重置」当成「短时等待」） | 按错误消息与 code 分类归因（`429001` / `quota_exceeded_error` / `ModelAccountTpmRateLimitExceeded`）；账号级限制需在账号维度处理，换模型无效 |
| **上下文长度估算误差** | 估算偏差可能导致误分流（该走 A 的走了 B，或反之） | 估算留安全余量；**估算失败时退回默认候选链**（宁可冒 429 风险，也不因估算错误拒绝服务）；分流决策在面板可见可关 |
| **声明值虚标** | 用户依文档填入的限额与实际不符，冷启动期排布偏差 | 声明仅用于冷启动；观测积累后以实测为准；差异写入 `conflicts` 显式可见 |
| **凭据类失败被误读为限流** | 曾导致「54 个目标全失败」被误判 | 错误分类前置；凭据类不计入限流统计；上下文限流与速率限流分开归因 |
| **单文件前端持续膨胀** | 改动风险随行数上升 | v1.0.0 前建立模块边界 |
| **配置迁移出错** | 升级后配置丢失或行为变化 | schema 版本 + 迁移链 + 升级前备份 + 回滚路径；**档案 schema 一次设计到位**以减少迁移次数 |
| **依赖 DSH 版本** | `llm/stream` / provider 注册表契约变更 | 明确声明支持的 DSH 版本区间；集成测试覆盖 |

## 9. 验收判据

### 9.1 阶段 A（v0.9.9）

- 开启峰谷后，`/status.timeWindows.segment` 随时间点变化；切换明细每行标注所属段

- **新渠道可仅凭用户声明即投入排布**（不依赖先跑探测）；声明内容（限额 / 重置规则 / 来源）可在面板填写与回读
- **渠道档案含 `declared` / `observed` / `conflicts` 三层结构**，且预置 `contextThrottle` 字段（即便暂未填充）

### 9.2 阶段 B（v1.0.0）

- 三类契约（端点 / 配置 / 落盘，**含渠道档案**）有 schema 文档
- 配置迁移链可用：版本升级后配置不丢失（含 `timeZone` / `mode`）
- 多 provider 段场景实机通过
- 安装 → 升级 → 回滚全流程不依赖手工文件操作
- 单测 + 集成测试双层通过；「不读 API Key」有测试守住

### 9.3 阶段 C（v1.x）

- 实测推断结果自动写入 `observed`，与 `declared` 形成对照并在面板可见（含来源与置信度）
- **声明与实测不一致时，`conflicts` 在面板与报告中显式展示**，且排布以实测为准
- **429 三类可区分**：速率限制 / 配额耗尽 / 账号级 TPM 各自归因，并采取不同恢复策略
- **TPM 上限可从 429 消息反推**，并写入档案

- 上下文阈值可探测（突破当前 1024 / 8192 两档限制），且能区分「上下文本身所致」与「相间 TPM 累积所致」

- 报告给出错误分类结论（含 **TPM 限流**与配额耗尽的区分），无需人工判断
- 调用记录与探测记录可按目标/时段关联查询

## 附录 B：术语表

| 术语 | 含义 |
| --- | --- |
| provider | DSH 中的模型供应商接入点；同一平台的不同 API Key 是不同 provider |
| 候选链（route） | 一次调用可依次尝试的 `(provider, model)` 序列 |
| 首分片（first chunk） | 流式响应的第一个内容分片；此前的失败可切换，之后不可 |
| commit-on-first-chunk | 流式文法硬约束：首分片一旦产出即视为提交，不再切换 |
| 熔断（cooldown） | 连续失败达阈值后暂时跳过该渠道，冷却后放行试探 |
| 窗口（window） | 上游配额的计量周期（5 小时 / 周 / 自定义） |
| 配额组（quotaGroup） | 共享同一配额池的多个 provider 的集合 |
| 四相测试 | 健康探测 / RPM 阶梯 / 上下文容量 / 配额组联动 |
| 段（segment） | 峰谷定价中的时间段（峰段 / 谷段） |
| 无感知 | 调度行为对 agent loop 透明，调用侧不感知切换 |
| **渠道档案（Channel Profile）** | 单个渠道的限制与脾气的累积记录，含 `declared` / `observed` / `conflicts` 三层 |
| **声明层（declared）** | 用户依说明文档提供的限额/重置规则，接入即可用，可虚标 |
| **实测层（observed）** | 主动测试与历史观测累积的值，带样本数与置信度 |
| **冲突层（conflicts）** | 声明与实测不一致的条目，显式展示、不静默覆盖 |
| **上下文 × 限流耦合** | 输入上下文越长，触发限流的概率越高的现象；**根本机制是 TPM 消耗**（token 多则额度耗尽快），因可事前估算，是唯一可主动规避的限流类型 |
| **TPM（tokens per minute）** | 单位时间可消耗的 token 数上限；是「长上下文易触发限流」的根本解释，应作为档案记录的根本量 |
| **RPM（requests per minute）** | 单位时间可发起的请求数上限；与 TPM 是两个独立维度 |
| **429 三类** | ① TPM/RPM 速率限制（`429001`，短时等待可恢复）；② 配额耗尽（`quota_exceeded_error`，需等窗口重置）；③ **账号级** TPM（`ModelAccountTpmRateLimitExceeded`，换模型无效） |
| **上下文预判分流** | 请求前估算本次 token 量，结合渠道 TPM 上限与近期消耗决定是否改道，避免等 429 |
| **声明值虚标** | 部分平台对外宣称的限额与实际可用的限额不符的现象 |
