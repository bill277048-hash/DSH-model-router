**对「90% 是否合适」的回答**：
> **90% 这个数值本身没问题**（保守，业界常见）。**真正的问题是机制与负载不匹配** ——
> 节流防的是「**累积型**超限」，而真实 429 是「**瞬时拒绝**」。
> 在 `providerMeta` 为空（实机现状）下，该机制**既不产生收益也不产生危害**。

## 为什么 429 不是累积触发？

`minimax-cn` 在**我们零流量**的情况下 429，可能原因：

| 假设 | 可验证性 |
| --- | --- |
| provider 的限额是**账号/IP 级共享**（被其他客户端消耗） | 需上游文档/支持确认 |
| provider 的限额**远低于我们以为的量级**（如 100K TPM，单个 133K 请求即超） | 🟢 **与数据一致**：单请求 P90=133K，若限额 < 133K 则**每次都必 429** |
| 上游把**当前请求自身的 token** 先计入再判超限 | 🟢 与数据一致（失败请求 tok=0 但携带 13K 输入） |

**最可能**：**上游限额低于单请求 token 量级**（或把当前请求计入）。
若是这样，**任何「按分钟累计」的节流都无效** —— 因为**单次请求本身就已经超了**。

> ⚠ **观测缺口**：ndjson **不记录上游错误原文**（只有归一化后的 `errorCode`），
> 无法区分「累积型 429」与「瞬时限流」。这是下一轮应补的字段。
